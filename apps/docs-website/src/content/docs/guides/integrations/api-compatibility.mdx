Chatto's API is experimental. Until the project publishes a stable API policy,
any release may change RPCs, protobuf messages, error behaviour, authentication,
or the realtime protocol in ways that require client changes.

The `v1` in package names such as `chatto.api.v1` is part of the current wire
name. It does not mean that every Chatto release exposes the same API.

<Aside type="caution">
  Pin an exact Chatto version for any deployment used by an integration. Test
  your integration against a new version before upgrading that deployment.
</Aside>

## Target a server release

Use the protobuf definitions and API reference from the same Chatto release as
the server you target. Do not assume that a client generated from the latest
source works with an older server, or that an older client works unchanged with
a newer server.

Release notes can call out important API changes, but they are not a complete
compatibility report. When an integration matters in production, test its main
workflows against the exact upgrade candidate.

## Inspect the server version

Call `chatto.discovery.v1.ServerDiscoveryService.GetServer` before
authentication to read the server's public profile and software version.
Decide explicitly which Chatto releases your integration supports, and test
against each supported release rather than inferring method-level compatibility
from discovery metadata.

The discovery response also carries a `compatibility` message listing the
stable protocol capability keys this server supports:

- `chatto.discovery.v1`
- `chatto.auth.v1`
- `chatto.api.v1`
- `chatto.admin.v1`
- `chatto.realtime.v1`
- `chatto.realtime.projection.v1`
- `chatto.role-colors.v1`

These values tell you which broad protocol surfaces the server advertises. They
do not negotiate an API version, guarantee a particular method or field, or say
that the signed-in user has permission to use a feature.

`chatto.role-colors.v1` specifically indicates that role resources accept the
additive 24-bit RGB colour fields and public user resources expose an optional
effective `role_color`. Clients should omit colour mutations when it is absent.

Ignore capability values you do not recognise. If a capability you need is
absent, treat that protocol as unavailable. Upstream Chatto servers omit the
`compatibility` message entirely, so decide explicitly whether to reject those
servers or support a known range of releases through your own tests.

The bundled 0.5 web client requires a 0.5 server and
`chatto.realtime.projection.v1`. It does not fall back to the 0.4
room-at-a-time ConnectRPC bootstrap, so it reports 0.4 servers as unsupported
and asks the operator to upgrade them. A 0.5 server accepts only realtime
protocol 2; older clients must migrate to the server-scoped projection stream.

This breaking realtime migration does not retire the `chatto.api.v1`
ConnectRPC namespace. It remains Chatto's resource-oriented public integrations
API. Do not replace explicit resource reads, pagination, mutation responses, or
read-your-writes handling with assumptions about projection internals.

Protocol 2 resume cursors are opaque, viewer-bound, and valid for up to 24
hours. Retain a cursor only with the projection state produced before it, and
replace it after each `caught_up` frame. A missing, expired, or unusable cursor
does not fail convergence: the server sends a compacted `reset` and current
projection state through the same operation stream. An integration that is
offline for more than 24 hours recovers current state but cannot request every
historical transition from that interval.

Authenticated `server_state_upsert` operations can include optional full
catalogs such as `custom_emojis` and `soundboard`. Treat an absent catalog as
unsupported and preserve any separately loaded fallback. Treat a present empty
catalog as authoritative empty state. This presence rule lets newer clients
converge catalog changes while older clients safely ignore fields they do not
recognise.

`CustomUserStatus.emoji` accepts either one supported Unicode emoji or the
canonical name of a current server custom emoji, up to 64 characters. A client
must resolve custom names through that server's `custom_emojis` catalog, hide an
unresolved or deleted marker, and keep rendering the status text. Older servers
reject custom names with `INVALID_ARGUMENT`; older clients can decode the same
string field but may show the bare name, and generated clients that enforce the
older 16-character response bound may reject longer names. Deploy bundled
client and server updates together when custom status markers matter.

### Discovery capabilities and upstream Chatto

Upstream Chatto removed `compatibility.protocolCapabilities` and the containing
`compatibility` message during 0.5 development, in favour of gating features on
the server's release version alone. This distribution keeps both, because it
ships protocol features no upstream release carries and a release version
cannot distinguish them from an upstream server reporting the same version.

Write clients so that a missing `compatibility` message means "no capabilities
declared" rather than an error. That keeps a single client working against both
this distribution and upstream servers. Regenerate protobuf clients from the
schema of the server you target, and do not mix generated clients and servers
across that difference.

`compatibility` is field 1000, outside the tag range upstream allocates, so an
upstream field addition cannot collide with it. Any client generated before
this change carried the message on field 3 and reads no capabilities from a
current server; regenerate to restore them.

`ServerCompatibility` is defined in `chatto/discovery/v1/compatibility.proto`.
Generated TypeScript therefore exports it from `discovery/v1/compatibility_pb`
rather than `discovery/v1/server_pb`. Generated Go is unaffected, since both
files share one package.

## Before upgrading

1. Check the release's data-migration and rollback constraints, and prepare a
   tested recovery plan.
2. Regenerate or update your client from the candidate release's protobufs.
3. Test authentication, required RPCs, error handling, pagination, and realtime
   reconnect behaviour that your integration depends on.
4. Deploy the server and client changes together when the API changed.
